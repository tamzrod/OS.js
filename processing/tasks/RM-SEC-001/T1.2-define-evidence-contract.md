## Purpose

Define where baseline evidence lives, which metadata every artifact carries, how outputs are named and hashed, and which evidence is committed versus retained by CI.

## Inputs

- [`P2 G1 plan`](../../../docs/p2-g1-baseline-reproducibility-plan.md), decision D5.
- Toolchain contract completed by T1.1.

## Dependencies

- Satisfied: T1.1 completed the toolchain contract for Node 26.13.0 and npm 11.20.0.

## Scope

### In scope

- Establish `docs/evidence/security-baseline/` and its README.
- Define an evidence manifest schema and deterministic artifact naming.
- Require commit, dirty state, lockfile hash, UTC time, platform, architecture, Node/npm versions, registry, command, exit code, and artifact hash.
- Define committed summaries versus CI-retained machine output.
- Define commands and expected non-zero audit/build semantics.

### Out of scope

- Running audits or generating SBOMs.
- Changing dependencies or the lockfile.
- Creating a general-purpose evidence platform unrelated to G1.

## Change surface

- `docs/evidence/security-baseline/README.md` — evidence contract and retention policy.
- `docs/evidence/security-baseline/manifest.schema.json` — machine-checkable manifest schema, if a schema is selected.
- `scripts/security/` — only a minimal manifest/hash helper if required.

## Steps

1. Define artifact classes, names, and retention location.
2. Define mandatory provenance fields and JSON schema.
3. Define hashing and validation commands.
4. Document how audit/build non-zero results are recorded without being mistaken for command-execution failure.
5. Validate example manifest data against the schema.

## Exit condition

A reviewer can determine exactly how to generate, identify, hash, validate, retain, and compare every G1 evidence artifact without making an undocumented choice.

## Review and Continue

- **Result:** T1.2 exit condition is satisfied. A reviewer can generate, identify, validate, hash, retain, and compare G1 evidence without choosing an undocumented format.
- **New findings:** CI artifact retention is repository-policy-dependent. The contract therefore requires maximum configured retention plus transfer of release evidence to a durable archive before expiry. Final G1/release evidence must come from a clean worktree; dirty-worktree evidence is development-only.
- **Next decision:** **Continue.** T1.2 stayed within its documentation and validation scope. The valid example is accepted, invalid manifest input is rejected with actionable errors, internal links resolve, and the lockfile is unchanged. Advance to P4 G1 / T1.3.
