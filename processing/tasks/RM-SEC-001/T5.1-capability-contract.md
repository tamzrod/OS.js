# T5.1 — Production capability contract and fail-closed startup tests

**Goal:** G5 — Reduce and patch the server surface  
**State:** Ready for P4 implementation; not accepted  
**Depends on:** Accepted G4 closure and P2 G5 plan  
**Scope:** Contract, startup validation, negative regression tests and consumer inventory only; no broad package upgrades

## Problem and exact locations

- `src/server/index.js` registers Core, Package, VFS, Auth and Settings providers without a production capability check.
- `src/server/config.js` only declares root, port and public.
- `vendor/osjs-server/src/config.js` defaults to a publicly known `session.options.secret`, development mode outside NODE_ENV=production, and large multipart limits.
- `vendor/osjs-server/src/providers/auth.js` registers public `/register` and `/login`.
- `vendor/osjs-server/src/providers/core.js` registers WebSocket `/`, body parsing and static routes.
- `vendor/osjs-server/src/core.js` constructs session and WebSocket before boot/listen. Production validation must happen **before Core construction**, not after provider registration.
- `vendor/osjs-server/src/auth.js` must be inspected for the default adapter before deciding how an explicit real adapter is configured.

## Required implementation

1. Define a strict, self-contained deployment profile/capability validator that runs before `new Core(...)` in production. Keep development behavior unchanged for this task. A missing, unknown or insecure profile must throw without beginning an HTTP/WebSocket listen or registering providers. An explicit production profile must not be treated as secure merely because an environment flag is set.
2. Represent every production capability in the P2 G5 allowlist. Unknown keys reject; omitted features are disabled. Browser-only/static distribution does **not** start the OS.js Node server.
3. For any optional server profile, reject null/accept-any authentication, default or blank session secret, public registration, development mode, and unauthorized VFS/proxy/WS/upload capabilities. Do not introduce a credentials/secret value in source.
4. Record concrete consumers (server route, browser API call, product requirement) before enabling any optional capability. If no approved real authentication adapter exists, the optional server profile must remain **unavailable** rather than allowing unsafe startup.
5. Add table-driven tests for every rejected configuration, including unknown capability keys and hostile inherited object properties. Add positive tests **only** for a profile that is proven correctly wired and safe.
6. Capture dependency roots for the enabled and disabled paths to inform T5.2. No lockfile change is required for T5.1.

## Verification

- Test direct validator invocation with no Node server listening.
- Test `NODE_ENV=production` boot with missing/unsafe configuration exits nonzero before any port is bound.
- Test arbitrary usernames cannot be accepted as authentication without a verified adapter.
- Keep `npm test` and existing G1–G4 security test behavior unchanged.
- Confirm `git diff` contains no packaged credentials, unexpected provider enabling or dependency graph changes.

## Acceptance / stop criteria

T5.1 is complete only with a checked-in capability contract, a demonstrated startup enforcement hook, passing negative tests, and a reviewed consumer inventory. Otherwise leave it open, record actual blocker, and do not advance to T5.2. Do not deploy, merge PR #1, or edit `master`.
