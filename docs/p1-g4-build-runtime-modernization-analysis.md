# P1 G4 — Browser build and runtime modernization analysis

## Problem we are solving

The fork cannot produce its browser distribution on the pinned supported runtime. On Node 26.13.0/npm 11.20.0, the exact root build fails in Webpack 4's `crypto.createHash` path with `ERR_OSSL_EVP_UNSUPPORTED`. Enabling OpenSSL's legacy provider would restore an obsolete digest implementation globally and is prohibited by the roadmap; it is not a remediation.

G4 must replace the obsolete build chain while preserving observable browser behavior and package contracts. This is both an availability problem (the release cannot be built) and a supply-chain problem (the build graph contains known high/critical findings).

## Exact current surface

Five fork-owned build configurations are in scope:

| Configuration | Output contract | Special behavior |
|---|---|---|
| `webpack.config.js` | OS.js browser entry, HTML, CSS, chunks, favicon, fonts/assets, source maps | split chunks, `OSJS_VERSION`, production CSS minimization |
| `vendor/osjs-common/webpack.config.js` | CommonJS library and source map | Node target |
| `vendor/osjs-client/webpack.config.js` | `osjsClient` UMD library, CSS/assets, source maps | transpiles local `@osjs` modules |
| `vendor/osjs-dialogs/webpack.config.js` | `osjsDialogs` UMD library and CSS | external/runtime compatibility through client imports |
| `vendor/osjs-settings-application/webpack.config.js` | application JS/CSS bundle | preserves `osjs: OSjs` external |

The root lock resolves Webpack 4.46.0 and webpack-cli 3.3.12. Key coupled versions include html-webpack-plugin 3.2.0, mini-css-extract-plugin 1.6.0, optimize-css-assets-webpack-plugin 5.0.6, css-loader 5.2.5, sass-loader 10.2.0, babel-loader 8.2.2, and Terser 4 through Webpack's legacy minimizer. The settings package also retains older package-local loader/plugin versions through its historical development graph.

## Security relevance

The clean G3 full audit identifies Webpack and its old minimizer chain as high severity, html-webpack-plugin as a direct critical finding, and loader-utils as critical. The same build surface also reaches high findings through copy-webpack-plugin, html-minifier, serialize-javascript, PostCSS/SVGO, Terser, and old Sass-related chains. These tools process trusted repository source in CI, which limits runtime reachability but does not remove supply-chain or malicious-input risk.

The current production audit remains nonzero partly because local fork package metadata causes legacy build graphs to be represented in the root release lock. G4 must modernize package manifests and the root graph together; changing only the root Webpack version would leave duplicate vulnerable package-local chains.

## Baseline behavior to preserve

Modernization must preserve:

- root HTML template expansion, favicon and static asset emission;
- root CSS extraction, font paths, image paths, chunk loading, and `OSJS_VERSION` injection;
- CommonJS output for `@osjs/common`;
- named UMD globals and source maps for client and dialogs;
- the settings application's `OSjs` external contract;
- production minification and deterministic asset inventory;
- browser startup, CSP behavior, package discovery, and runtime asset loading.

Byte identity is not expected across a bundler/minifier migration. T4.1 therefore needs a reference artifact with normalized inventories, public/global contracts, source/source-map inputs, HTML structure, CSS/assets, and smoke-test observations—not only hashes of old generated bytes.

## Constraints and boundaries

- Node 26.13.0/npm 11.20.0 remains the enforced runtime unless a later explicit roadmap decision changes it.
- No command, script, CI setting, or documentation may introduce `--openssl-legacy-provider`.
- A temporary older runtime may be used only in an isolated reference-capture task if its exact identity and containment are recorded; its output cannot be release evidence.
- G4 owns browser/package build tooling. Server dependency and denial-of-service remediation remains G5; minimal browser packaging remains G6.
- Source maps require an explicit release policy because they can disclose source even when they are necessary for comparison and debugging.

## Primary risks

1. Webpack 5 changes asset modules, chunk/runtime output, Node polyfills, plugin APIs, and loader defaults.
2. Replacing file-loader and old CSS optimization can change emitted filenames and URLs.
3. Sass/PostCSS upgrades can change rendered CSS or reject deprecated syntax.
4. Library output changes can silently break CommonJS/UMD consumers even when compilation succeeds.
5. html-webpack-plugin upgrades can change template injection order or escaping.
6. Removing duplicate package-local build graphs can change package installation and publish behavior.
7. A root-only smoke test can miss broken standalone package builds.

## Decision carried into P2

Prefer a coordinated Webpack 5 migration over adopting a second bundler. The existing configurations are small and their public library/external contracts map directly to maintained Webpack 5 features, while a bundler replacement would add avoidable semantic drift.

P2 must define a reference-first sequence, an exact maintained dependency set, package-by-package migrations, explicit source-map/CSP/asset acceptance criteria, and clean retained evidence. The migration must remove obsolete versions from both root and package-local graphs and prove builds succeed without legacy OpenSSL mode.
