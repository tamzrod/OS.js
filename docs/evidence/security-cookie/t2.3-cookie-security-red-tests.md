## Complete-suite outcome

```text
Test Suites: 1 failed, 34 passed, 35 total
Tests:       6 failed, 308 passed, 314 total
```

The sole failing suite is `__tests__/auth-security.js`. Its six passing cases establish that the harness and unchanged compatibility paths work: inherited `enabled` is ignored during `init`, JSON `__proto__`/`constructor`/`prototype` cases do not enable persistence during `init`, disabled startup does not read or replay a legacy cookie, and failed login preserves its event order without writing browser state.

## Expected red failures

| Contract | Observed legacy behavior |
|---|---|
| Own `enabled: true` must fail closed before adapter initialization | `Auth.init()` resolves and initializes the adapter. |
| An `enabled` accessor must be rejected without invocation | `Auth.init()` resolves instead of rejecting the unsupported descriptor. |
| Successful login with persistence disabled must not touch cookies | Legacy code writes an expiry cookie through `Cookies.remove`. |
| Submitted credentials must never be serialized | Legacy code writes username, password, and custom values into `osjs.auth`. |
| Successful logout must not manipulate client cookies | Legacy code writes an expiry cookie through `Cookies.remove`. |
| Standalone login must not manipulate client cookies | Legacy code writes an expiry cookie even in standalone mode. |

These failures directly identify the implementation work assigned to T2.4. There are no unexpected failures.

## Browser boundaries and compatibility assertions

The tests instrument the native `document.cookie` getter/setter, the shared local/session Web Storage `setItem` boundary, and IndexedDB `open` rather than mocking `js-cookie`. This keeps the assertions valid after the dependency is removed. They also preserve and check adapter identity, login event ordering, core login/logout events, logout shutdown behavior, standalone success, custom nested accessors, symbols, and hostile configuration keys.
